# Pawtato API — Production Roadmap & Progress Blueprint

This file is the **execution source of truth** for taking Pawtato from its current state to a production-grade platform. `PAWTATO_PROJECT_SPEC.md` is the *product* source of truth (what to build); this file is the *delivery* source of truth (in what order, what's done, what's left).

## How to use this file (read this first, every session)

- **Do not re-read the whole file every time.** Read `Current Status` below, then jump straight to the section for the active phase. Earlier completed phases are historical record — skip them unless debugging something they built.
- Each phase is self-contained: Goal, Tasks, Swagger Requirement, Definition of Done, Status.
- Tasks use checkboxes. Tick them as completed (`- [x]`). Do not delete tasks — if scope changes, strike through and note why.
- When a phase is finished, update `Current Status`, flip its row in the Phase Index, and append one line to `Progress Log`. Keep the log entry short (1–3 lines) — it's a changelog, not a report.
- **Swagger is not optional in any phase.** Every phase below ends with an explicit Swagger Requirement. A phase is not "done" if endpoints it touched aren't documented.
- If a phase's scope turns out too large for one session, stop at a clean sub-task boundary, tick what's done, and leave the rest unchecked — the next session picks up exactly there.

## 0. Baseline Audit (snapshot taken 2026-08-22)

Recorded once so future sessions don't need to re-derive it by re-reading the whole codebase.

### Stack (actual, not the spec's illustrative example)

- **Runtime/Framework:** NestJS 11 (TypeScript), Express platform
- **Database:** MongoDB via Mongoose (`@nestjs/mongoose`)
- **Auth:** JWT (`@nestjs/jwt`, `passport-jwt`), bcrypt password hashing, refresh token support present
- **Docs:** `@nestjs/swagger` already installed and partially wired
- **Other deps already present:** `helmet`, `class-validator`/`class-transformer`, `nest-winston` + `winston` (installed, not yet configured), `joi` (installed, **not wired**), `qrcode`, `nanoid`, `@nestjs-modules/mailer` + `nodemailer`, `@nestjs/schedule`, `@nestjs/serve-static`
- Note: the spec's `Pawtato.Api / Application / Domain / Infrastructure` (.NET-style) layout is illustrative only. The actual project uses NestJS's module-per-feature convention (`src/modules/<feature>`), which is an acceptable equivalent layering (Controller≈API, Service≈Application, Schema≈Domain, Mongoose model≈Infrastructure). The roadmap works within this convention rather than forcing a .NET folder structure onto it.

### Implemented modules (`src/modules/*`)

`auth`, `users`, `pets`, `public`, `qr`, `medical`, `vaccinations`, `notifications` (+ a vaccination-reminder cron job), `admin`, `activity` (admin audit log), `health`, `database`.

Working end-to-end today: register/login (JWT + refresh), pet CRUD with ownership scoping, mark pet lost (fields on `Pet`), a public pet-profile lookup by `publicId` that increments a scan counter, a public lost-pets list, QR PNG generation, medical records, vaccinations with reminder job, admin dashboard stats/user/pet management with role changes, an admin action audit log.

### Key gaps vs `PAWTATO_PROJECT_SPEC.md` (drives Phases 1–3)

1. ~~**No independent QR Tag entity.**~~ **Fixed in Phase 2.** A first-class `Tag` model now exists with the full lifecycle, and `Pet.qrCode`/`Pet.publicId` have been removed in favor of it.
2. ~~**No Found-Report / Finder flow.**~~ **Fixed in Phase 3.** `POST /public/tags/:publicCode/found-report` now exists, no account required.
3. ~~**No scan-event audit trail.**~~ **Fixed in Phase 3.** A `ScanEvent` is now recorded on every public scan (`src/modules/scans/`), independent of `Pet.scanCount` (kept as a cheap derived counter).
4. **No rate limiting.** Spec §16/§17 explicitly requires rate limiting on public endpoints, assuming automated abuse. No `@nestjs/throttler` (or equivalent) is installed or configured anywhere. → **Phase 1**.
5. **No CORS configuration, no global exception filter, no global response interceptor actually wired.** `ResponseInterceptor` exists in `src/common/interceptors/` but is never registered (`app.useGlobalInterceptors` is never called in `main.ts`) — the standardized `{ success, message, data }` envelope is currently dead code, not the real API shape. → **Phase 1**.
6. **`Joi` is a dependency but unused.** `ConfigModule.forRoot` has no `validationSchema`, so a missing `.env` var (e.g. `JWT_SECRET`) fails silently/late instead of at boot. → **Phase 1**.
7. **Dead/duplicate files at `src/` root**, orphaned from before the module refactor, all 0 bytes and unreferenced: `pets.controller.ts`, `pets.module.ts`, `pets.service.ts`, `schemas/pet.schema.ts`, `dto/create-pet.dto.ts`, `dto/update-pet.dto.ts`. → **Phase 1 cleanup**.
8. **`main.ts` has a duplicated `ValidationPipe` registration** (registered twice back-to-back) and a hardcoded `http://localhost:5000` URL baked into `qr.service.ts`'s generated QR payload, which will point to the wrong host in any non-local environment. → **Phase 1**.
9. **No Dockerfile for the app itself** (only `docker-compose.yml` for a local MongoDB container), **no CI pipeline** (`.github/` is empty). → **Phase 1**.
10. **Notifications are email-only**, not abstracted behind a channel interface as spec §14 recommends for future Push/SMS. → **Phase 4**.
11. **File storage is local disk** (`/uploads`, served via `ServeStaticModule`), not behind a storage-provider abstraction as spec §18 recommends. → **Phase 5**.
12. **Swagger is partially applied** — some controllers use `@ApiTags`/`@ApiOperation` (e.g. `public.controller.ts`), coverage across all controllers/DTOs/response shapes/error responses is inconsistent. → **Phase 1 sets the standard; every later phase maintains it.**

## Phase 2 — QR Tag Domain Correction

**Goal:** Bring the QR system in line with spec §4/§9 — a `Tag` independent from `Pet`, with an explicit lifecycle and assignment history, resolved via a stable public code (not an internal ID).

### Tasks
- [x] Created a `Tag` schema/module (`src/modules/tags/`): `publicCode` (unique, indexed, server-generated via `nanoid`, never client-supplied), `serialNumber` (unique, indexed, client-optional/auto-generated), `status` enum `TagStatus` (`MANUFACTURED | AVAILABLE | ASSIGNED | SUSPENDED | RETIRED`, in `common/enums/tag-status.enum.ts`), `assignedPetId` (nullable ref to `Pet`), `qrImageUrl`, `createdAt`/`updatedAt` (via `timestamps: true`), `assignedAt`, `unassignedAt`.
- [x] Added tag endpoints on `TagsController` (`/tags`): `POST /tags` (admin, create — seeds directly as `AVAILABLE`; see assumption below), `GET /tags` (admin, paginated inventory with optional `status` filter), `GET /tags/mine` (authenticated, tags assigned to the caller's own pets), `GET /tags/:id` (admin), `POST /tags/assign` (authenticated, body `{ publicCode, petId }` — a real user only ever knows the code printed on the physical tag, never an internal Mongo ID, so assign/unassign are keyed on `publicCode` rather than `:id`), `POST /tags/unassign` (authenticated, body `{ publicCode }`, allowed for the owner of the currently-assigned pet or an admin), `PATCH /tags/:id/suspend` (admin), `PATCH /tags/:id/retire` (admin).
- [x] Enforced "at most one active tag per pet" two ways: an application-level check in `TagsService.assign()` (rejects with 400 if the pet already has an `ASSIGNED` tag), plus a DB-level partial unique index on `Tag.assignedPetId` (`partialFilterExpression: { assignedPetId: { $type: 'objectId' } }`) so the constraint holds even under concurrent requests, while still allowing unlimited unassigned (`null`) tags to coexist. "At most one active assignment per tag" is structurally guaranteed (a tag has exactly one `assignedPetId` field). **Assumption**: a pet has at most one tag at a time — reassignment means unassign-then-assign, not multiple simultaneous tags per pet (matches the spec's single-tag worked example; documented here per spec §28 rule 20).
- [x] Updated `QrService.generate()` to encode the tag's public resolution URL and, more importantly, moved *when* it's called: QR generation now happens once, at tag creation (`TagsService.create()`), not at pet creation. This is a real architectural fix, not just a rename — the physical sticker's QR image must stay valid forever across reassignment to different pets, since resolution is dynamic (tag → currently-assigned pet, looked up at scan time), so the image content must never depend on which pet is currently attached.
- [x] **Documented deviation from the task's literal URL**: the task specifies encoding `https://<APP_URL>/t/{publicCode}`. This repo is API-only (no frontend project present anywhere in the working tree), so `/t/{code}` would resolve to nothing. Kept the QR payload pointing directly at this API's own public resolution route — `${APP_URL}/api/public/tags/{publicCode}` — mirroring exactly how the pre-Phase-2 code already worked (it pointed at `/api/public/pets/{publicId}` directly, not a frontend route). `APP_URL` is already a single config value, so once a real frontend exists, pointing QR codes at it is a one-line config/URL-building change, not a rearchitecture.
- [x] Replaced the public lookup route: `GET /public/pets/:publicId` → `GET /public/tags/:publicCode`, resolving `Tag.publicCode → Tag.assignedPetId → Pet`. Handles three tag states explicitly instead of just 404ing: `RETIRED`/`SUSPENDED` return a clear status message, and an tag that exists but isn't currently `ASSIGNED` returns "not linked to a pet yet" rather than crashing or leaking anything — this matters because a real finder can absolutely scan a tag that was never assigned. The pet's internal Mongo `_id` is never present anywhere in the public response.
- [x] **Removed `Pet.publicId` and `Pet.qrCode` from the `Pet` schema entirely** rather than keeping them as unused legacy fields — `Tag.publicCode`/`Tag.qrImageUrl` fully replace their role, and per this project's own stated principle (avoid backwards-compat cruft for fields nothing reads), keeping them would just be dead weight. Removed the matching `nanoid`/`QrService` calls from `PetsService.create()` (pet creation no longer generates a QR code — assigning a physical tag is now a separate, later step, matching the real product flow in spec §2/§27). Cleaned up the two other places that referenced the now-gone `publicId` field: the admin pet search filter (search is now by name only — an admin can search tags separately via the new `GET /tags`) and `topScannedPets()`'s field selection.
- [x] **Fixed a regression the field removal would otherwise have caused**: `PublicService.getLostPets()` used to return each pet's `publicId` so a finder could click through to its profile. With that field gone, the public lost-pets listing needed a replacement identifier — it now does a batched lookup of each listed pet's currently-`ASSIGNED` tag and returns that tag's `publicCode` instead (and explicitly does not leak the pet's internal `_id`, which a naive `.lean()` spread would have included).
- [x] **Migration/backfill — clean break, not a migration script**: chose not to write a backfill for pets with a pre-existing `qrCode`. This project has no production users or live pet data yet (confirmed in the Phase 1 baseline audit — this is pre-launch), so any existing dev/test `Pet` documents with the old fields can simply be recreated against the new `Tag`-based flow; a migration script would be pure overhead for data that doesn't need preserving.
- [x] Added indexes: `Tag.publicCode` (unique + index), `Tag.serialNumber` (unique + index), and the partial unique index on `Tag.assignedPetId` described above (which also serves as the "queryable by assigned pet" index).
- [x] Verified the whole change set at the decorator level without needing a live database: `node -e "require('./dist/app.module.js')"` loads and evaluates every schema/controller/DTO decorator in the entire app (the same mechanism that crashed in Phase 1 on `Activity`/`User`) with zero errors — a stronger, network-independent check than the live-boot attempt Phase 1 couldn't complete in this sandbox. Live DB connection + Swagger UI render is still unverified here (no network egress in this sandbox at all — confirmed via a raw DNS/socket test) and remains an open item from Phase 1.

### Swagger Requirement
Applied: every `tags` endpoint has full `@ApiTags`/`@ApiOperation`/`@ApiResponse` coverage (including the "not available"/"not found" error cases), every new DTO (`CreateTagDto`, `AssignTagDto`, `UnassignTagDto`, `TagQueryDto`) is fully `@ApiProperty`-annotated, and the updated `public.controller.ts` route's Swagger description explicitly documents the three possible response shapes (assigned/unassigned/suspended-retired) so API consumers don't assume it's always a full pet profile.

### Definition of Done
- [x] Tags exist as first-class records with a real lifecycle, assignable/unassignable independent of pet deletion.
- [x] QR codes resolve via `publicCode`, never an internal ID (encoding an API URL rather than the literal `/t/{code}` frontend path — see documented assumption above).
- [x] Ownership and assignability are validated server-side on every tag mutation (`assign`/`unassign` both go through `PetsService.findOwnedPet`, which throws a uniform `NotFoundException` for both "doesn't exist" and "not yours," matching this codebase's established IDOR-prevention convention).

### Status
**Complete** (2026-08-22). `npm run lint`, `npm run build`, and `npm test` (22/22 suites, up from 20 — added `tags.controller.spec.ts`/`tags.service.spec.ts`) all pass clean. Two items carried forward, both inherited from Phase 1 and not new to this phase: live DB-connected boot and an actual look at `/api/docs` in a browser are still unverified in this sandbox (no network egress at all here, confirmed directly) — do both once against a real MongoDB before treating Phase 1 *or* 2 as fully closed in production.

## Phase 3 — Lost & Found Flow Completion

**Goal:** Complete the core "find a lost pet" loop from spec §6–§8: finder reports, scan history, and owner-facing visibility into both — without requiring the finder to register.

### Tasks
- [x] Added a `ScanEvent` schema/module (`src/modules/scans/`): `tag` (ref, indexed), `pet` (nullable ref, indexed — `null` when the scanned tag isn't currently linked to a pet), `approxLocation` (optional, not auto-populated — see assumption below), `userAgent` (captured from the request header), `createdAt` (indexed, via `timestamps: true`). Wiring it up meant two structural decisions worth recording:
- **Renamed `Activity.admin` → `Activity.actor`.** The field only ever meant "who did this" — once non-admin sensitive actions (tag assign/unassign/claim, a pet's lost/found status changes) log to the same collection alongside admin actions, `admin` stopped being an accurate name. Clean rename, no migration needed (no production data exists yet, consistent with the same call made for `Pet.qrCode`/`Pet.publicId` in Phase 2).
- **Chose direct `ActivityService` injection over the Phase 4 domain-event bus for audit writes.** Domain events (`pet.marked-lost`, `tag.assigned`, etc.) already exist and already drive notifications — routing audit logging through a second listener on the same events was considered, but rejected: an audit trail is exactly the kind of record where "fire-and-forget, might silently fail to persist" (the deliberate, correct tradeoff for notifications) is the wrong tradeoff. `ActivityService.log(...)` is now called directly and awaited at every sensitive call site — `TagsService` (assign/unassign/delete/claim/suspend/retire/bulkCreate), `PetsService` (reportLost/reportFound), `AdminService` (every user/pet moderation action), and `FoundReportsService` (moderation status changes) — each new module dependency is on the already-zero-dependency `ActivityModule` (a leaf module, so none of this introduces any circular-import risk, verified by `npm run build` and the existing `app.di-check.spec.ts`).
- Added pagination + `actor`/`action` filters to `GET /activity` (`ActivityQueryDto`) — the endpoint had none before, harmless when it always returned nothing, not harmless now that every admin action and every tag/lost-status change writes a row.

### Admin tag-inventory: a real gap between the spec's "Manufactured" tag state and what Phase 2 actually built
The spec (§4) lists `Manufactured` as a distinct tag lifecycle state alongside `Available`, but Phase 2 built tags as strictly self-service — every tag is owned by its creator from the moment it exists, with no "printed but not yet claimed" state at all. This phase adds that missing state rather than reusing `AVAILABLE` for it, since the two mean different things (owned-but-unlinked vs. not-yet-owned):
- `TagStatus.MANUFACTURED` added back to the enum; `Tag.ownerId` changed from required to nullable (`null` only while `MANUFACTURED`); added an optional free-text `Tag.batchLabel` for admin's own print-run tracking.
- `POST /tags/bulk` (admin only) — generates `count` (1–500) tags starting `MANUFACTURED`, no owner, reusing the exact same code-generation/collision-retry mechanics as self-service `create()` (extracted into a shared private `generateAndInsertTag()` rather than duplicated).
- `POST /tags/claim` (any authenticated user) — the missing link between manufactured inventory and the existing `assign` flow: moves a `MANUFACTURED` tag to `AVAILABLE` with the caller as owner. Self-service-created tags never need this — they're owned from creation.
- `GET /tags` (admin, already existed from Phase 2) needed no changes to support filtering by the new status — `TagQueryDto.status` already accepts any `TagStatus` value.
- `PublicService.getPetProfile` needed no changes either — its existing "any non-ASSIGNED status" fallback branch already returns `{ tagStatus: tag.status, message: 'not linked to a pet' }` generically, so a scanned `MANUFACTURED` tag correctly reports itself as not-yet-usable with zero new code. Updated the public endpoint's Swagger description to list the now-five possible `tagStatus` values (`MANUFACTURED` added) so frontend consumers don't hardcode four.

### Abuse/report-handling surface
`FoundReport` gained a moderation lifecycle: `status` (`PENDING | REVIEWED | DISMISSED | ACTIONED`, defaults `PENDING`), `reviewedBy`, `reviewedAt`. New admin-only endpoints on `AdminController` (not a new `/admin/tags`-style split — found-report review is a dashboard/moderation concern with no existing non-admin "list all reports" home, unlike tags which already had an established `/tags` admin surface from Phase 2): `GET /admin/found-reports` (paginated, filterable by `status` and/or `deviceFingerprint` — the latter lets an admin pull every report from one spammy device across every tag it's hit, using the same fingerprint that already drives the Phase 3 rate limiter) and `PATCH /admin/found-reports/:id/status`. Deliberately does **not** auto-cascade into suspending the associated tag — an admin who decides a report warrants that pairs it with the existing `PATCH /tags/:id/suspend` explicitly, rather than this endpoint silently taking two actions at once.

### Definition of Done
- [x] Admins can manage the full tag lifecycle without direct DB access — including the previously-missing "manufacture inventory before anyone owns it" step.
- [x] Sensitive non-admin actions are auditable, and so is every admin action — both through the same, now actually-wired, audit log.

## Phase 10 — Pet Dating & Companion Matching

**Provenance note:** unlike Phases 1–9, this phase is **not** derived from `PAWTATO_PROJECT_SPEC.md` — it doesn't mention pet dating/matching anywhere. It was requested directly by the user on 2026-08-22, alongside a companion PWA-first frontend blueprint (`PAWTATO_FRONTEND_BLUEPRINT.md`). Treat this phase as a real, intentional scope addition, not spec drift — but if a future session finds it conflicts with an updated spec, the spec wins and this phase gets revisited.

**Concept (as scoped with the user):** owners can opt any of their pets into a matching feature. Each pet's dating profile declares its own **purpose** — `PLAYDATE`, `BREEDING`, or `BOTH` — and discovery/matching respects that (a playdate-only pet is never surfaced to a breeding-only search, and vice versa, unless one side is `BOTH`). This is a swipe-to-match model (mutual like -> match -> lightweight chat), scoped for cats and dogs only, matching the rest of the platform.

**Goal:** Ship the matching feature as its own bounded module with minimal coupling to the rest of the app — it reads `Pet`/`User` (species, owner, location-adjacent fields) but nothing in the existing modules should need to know matching exists.

### Tasks

**Domain model** (new `src/modules/dating/` module)
- [x] `PetDatingProfile` schema: `petId` (ref, unique — one profile per pet), `purpose` enum (`PLAYDATE | BREEDING | BOTH`), `bio` (short text), `temperamentTags` (string array, e.g. `playful`, `calm`, `good-with-kids`), `photos` (array of image URLs, separate from the pet's main `profileImage` so owners can curate a dating-specific gallery), `approxLocation` (coarse — city/area string, or lat/lng rounded to ~1km; never the owner's precise address, matching spec §17's location-minimization principle), `isActive` (boolean — owner can pause visibility without deleting the profile).

## Phase 11 — Dating Rework: Mode Split, Rich Profiles & Identity Verification

**Provenance note:** requested directly by the user on 2026-08-25, refining Phase 10 rather than replacing the module wholesale. Phase 10 shipped a `purpose: PLAYDATE | BREEDING | BOTH` compatibility model where **both modes required same-species matching**. This phase changes that in a way that's incompatible with the old enum semantics, adds fields the Phase 10 schema doesn't have, and adds an entirely new identity-verification subsystem. Phase 10's Status/Definition-of-Done sections above are left untouched (they accurately describe what shipped and when) — this phase documents what changes on top of it. Treat this as the current source of truth for the dating module's intended shape; Phase 10 is historical record of the first cut.

**Concept (as scoped with the user):**
1. Discovery/matching splits into exactly two explicit modes — **Breeding** and **Play Date** — not a three-way purpose enum. A pet's dating profile can opt into either or both.
2. **Breeding mode**: the candidate pool is restricted to the **same species** as the swiping pet. Breed is *not* filtered — a pool of the same species naturally contains multiple breeds, and that's fine; only species must match.
3. **Play Date mode**: universal. Species is not a filter at all — any pet can be discovered by any other pet in Play Date mode, regardless of species.
4. The dating profile becomes a larger, dedicated profile — not just a thin layer over the pet's core profile: multiple curated photos (already schema-ready from Phase 10), a **Likes** list and a **Dislikes** list (new, distinct from Phase 10's `temperamentTags`, which stays as behavioral trait chips), and a visible medical/vaccination summary sourced from the pet's real `medical`/`vaccinations` records (reusing those modules, never duplicating the data — same principle Phase 10 already established for `healthVerified`).
5. **Profile Verification** (opt-in, separate from `healthVerified`): a user uploads both sides of their **NID** (National ID); an admin manually reviews and approves/rejects it. Verified users can filter discovery to a **verified-only pool**. When two verified profiles match, each side can independently tap **"share my ID"** within that specific match (decided 2026-08-25 — explicit per-match consent, not automatic on match); once shared, the other side can view it from the matched profile's detail screen.

**Goal:** ship this as a rework of `src/modules/dating/` (extending, not rewriting, most of Phase 10's plumbing — swipe/match/message/report machinery is unaffected) plus a new, narrowly-scoped identity-verification module, without weakening any of Phase 10's existing safety guarantees (species enforcement, IDOR-safe match access, coarse-location-only, cascade-delete integration).

### Tasks

**Mode split (replaces Phase 10's purpose-compatibility matching)**
- [x] Replaced `PetDatingProfile.purpose: DatingPurpose` with `modes: DatingMode[]` (`BREEDING`, `PLAYDATE` — a profile can hold one or both), schema-validated non-empty. **Clean break, no migration script**: confirmed (per Phase 2's own precedent) no production dating data exists yet, so the old `DatingPurpose` enum was deleted outright rather than migrated — `grep` confirmed zero remaining references before deletion.
- [x] `GET /dating/discover` takes a required `mode` param (`BREEDING | PLAYDATE`). `BREEDING`: same-species-only (via `PetsService.findIdsBySpecies`), breed unfiltered. `PLAYDATE`: no species filter at all — species eligibility was already enforced once at profile-creation time, so no re-check is needed at discovery time.
- [x] `Swipe` gained a required `mode` field. The unique index was widened to `(fromPetId, toPetId, mode)` (from `(fromPetId, toPetId)`) — a real correctness fix beyond the original task wording: without it, a pet pair enabled for both modes could PASS in one mode and be permanently blocked from a genuinely separate LIKE decision in the other. `Match` stays mode-agnostic in storage (per the original plan) but `listMatches()` reconstructs `mode` per match by looking up the originating reciprocal-LIKE `Swipe` pair, for the frontend's mode icon.
- [x] `DATABLE_SPECIES` (cat/dog) allow-list unchanged, still enforced once at profile-creation regardless of mode.

**Rich profile fields**
- [x] Added `likes: string[]` / `dislikes: string[]` (max 10 entries, same shape as `temperamentTags`).
- [x] Added `shareHealthSummary: boolean` (default `false`). **All-or-nothing, decided 2026-08-25.** When `true`, profile reads (`discover`, the new `GET /dating/profiles/:petId`) include a `medicalSummary` computed live via two new additive, ownership-unchecked read methods (`MedicalService.findAllByPet` / `VaccinationsService.findAllByPet` — authorization lives at the call site, since this is only ever invoked when the pet's own owner already opted in): `medicalRecordCount`, `vaccinationCount`, `vaccinationsUpToDate`, `lastVaccinationDate`. **Deviates from the task's literal field list**: no `spayed/neutered` status is included — no such field exists anywhere in this codebase's `Pet` schema, and fabricating one wasn't part of this task's scope, so the summary reports only what's actually derivable from real records.
- [x] `photos` bounded to 1–6 in `CreateDatingProfileDto` (`@ArrayMinSize(1)`/`@ArrayMaxSize(6)`); `UpdateDatingProfileDto` keeps it optional via `PartialType`.
- [x] **Not in the original task list, added because the frontend blueprint needed it**: `GET /dating/profiles/:petId` — there was no way to fetch a single candidate/matched pet's full dating profile at all (Phase 10 only had create/update/verify-health). Viewable by anyone while `isActive`; the owner can also view it while paused.

**Identity verification (new subsystem)** — built as `src/modules/dating/identity-verification.{service,controller}.ts` + `schemas/identity-verification.schema.ts`, inside the `dating/` module (sibling files, not a nested folder) since it's small enough not to warrant its own module.
- [x] `IdentityVerification` schema exactly as specified, with `nidFrontKey`/`nidBackKey` (private storage *keys*, not URLs — see below) instead of the task's literal `nidFrontUrl`/`nidBackUrl` naming, since nothing about them is ever a directly-usable URL.
- [x] `POST /dating/verification` (multipart `front`+`back`) — submits/resubmits. Resubmitting while `APPROVED` is rejected (400, "contact support"); resubmitting after `REJECTED` deletes the old private files and resets to `PENDING`. Rate-limited on the `write` tier (5/min).
- [x] `GET /dating/verification/me`.
- [x] Admin queue: `GET /admin/dating/verifications`, `PATCH /admin/dating/verifications/:id/approve`, `PATCH /admin/dating/verifications/:id/reject` (body: `reason`) — wired into `AdminController`/`AdminService`, mirroring the `DatingReport` queue pattern exactly. Plus `GET /admin/dating/verifications/:id/images` for on-demand signed review images (see safety guards below).
- [x] `GET /dating/discover?verifiedOnly=true` — 400 if the caller isn't themselves `APPROVED`; otherwise narrows the candidate pool via a batched owner-lookup (`PetsService.findOwnersForPets`, a new additive method) + `IdentityVerificationService.getApprovedUserIds`.
- [x] **NID exchange — decided 2026-08-25 (user call): explicit per-match share button, not automatic.** `Match.nidSharedBy: Types.ObjectId[]`. `POST /dating/matches/:matchId/share-nid` (caller must own a side + be `APPROVED`; idempotent). `GET /dating/matches/:matchId/nid` returns the *other* party's signed URLs only once they've shared **and** are still live-`APPROVED` — both directions checked fresh on every call, never trusting a stale flag. The caller must also be `APPROVED` themselves (the whole exchange section doesn't exist for an ineligible match, per the frontend blueprint).
- [x] Verified-badge groundwork: `discover()` and `getProfile()` responses include `ownerVerified: boolean` per profile (computed server-side, never by exposing the raw owner id to the client).

**The private-storage prerequisite this task called out as possibly needed — it was.** Every other upload in this codebase (avatar/pet/found-report photos) is public-read by design; NID images are the first genuinely sensitive document type. Extended `StorageProvider` (Phase 5's abstraction) with `uploadPrivate()`, `getSignedUrl(key, ttl)`, `deletePrivate(key)`:
- **Local** (dev default): private files write to `private-uploads/`, a sibling directory to `uploads/` that is *not* registered with `ServeStaticModule` (confirmed by reading `app.module.ts`'s static-serve config — it only mounts `uploads/`). `getSignedUrl()` mints a short-lived signed token (`@nestjs/jwt`'s `JwtService`, reusing `JWT_SECRET` purely as an HMAC signing key — not as an auth token) pointing at a new unauthenticated-but-token-gated route, `GET /storage/private/:token` (`StorageController`), which verifies the token and streams the file. An invalid/expired token is a plain `404`, not a distinguishing error.
- **S3**: added `@aws-sdk/s3-request-presigner` (new dependency, installed with npm 10.9.2 per the project's established lockfile-consistency fix) for real presigned `GetObjectCommand` URLs. `uploadPrivate()` is the same call as `upload()` — S3 has no separate "private root" the way local disk does — so the privacy guarantee rests on never calling `getUrl()`/constructing a public URL for these keys, only ever `getSignedUrl()`. **Documented as a deployment prerequisite, not something code can enforce**: the bucket (or at minimum the `identity-verification/` key prefix) must not have a public-read bucket policy in production — the same class of "flagged, not solved in code" item as the GitHub Actions permissions prerequisite from an earlier phase.

**Safety & scope guards**
- [x] NID images never appear inline in any list endpoint (`adminList()` explicitly `.select('-nidFrontKey -nidBackKey')`) — always fetched on demand per-submission via the signed-URL routes.
- [x] `POST /dating/verification` rate-limited (`write` tier, 5/min).
- [x] Cascade-delete: `IdentityVerificationService.deleteForUser(userId)` deletes both the record and its private files, wired into `AdminService.delete()` only (not `deletePet()` — verification is user-scoped, not pet-scoped, so deleting one pet must never touch it).
- [x] Mode filtering (species-required for BREEDING, species-agnostic for PLAYDATE) proven server-side by both a unit-level regression test per mode and a real HTTP e2e test (a dog is discoverable/swipeable in PLAYDATE but rejected in BREEDING against a cat).
- [x] **Found and fixed one gap during implementation, not in the original task list**: the admin NID-review endpoint (`adminGetSignedImages`) initially had no audit logging at all — a real gap against this phase's own Definition of Done ("every NID view produces an Activity log entry"). Fixed before considering the phase done: it now takes `actorId` and logs `dating.nid.viewed` with `{ context: 'admin-review' }`, same as the matched-party exchange.

### Swagger Requirement
Applied: every new/changed route (`GET /dating/discover`'s `mode`/`verifiedOnly` params, `GET /dating/profiles/:petId`, `POST /dating/verification`, `GET /dating/verification/me`, `POST /dating/matches/:matchId/share-nid`, `GET /dating/matches/:matchId/nid`, `GET /storage/private/:token`, and all four admin verification-queue routes) carries full `@ApiTags`/`@ApiOperation`/`@ApiResponse` coverage, with explicit descriptions stating that NID/private-file endpoints return short-lived signed URLs, never permanent links.

### Definition of Done
- [x] A Play Date candidate pool includes mixed species; a Breeding candidate pool never does — proven by both a `dating.service.spec.ts` unit test and a real-HTTP e2e test (a dog pet is discoverable/swipeable in PLAYDATE, rejected server-side in BREEDING).

## Phase 12 — Dating Hardening: Gender-Based Breeding Safety, Real-Time Chat & Chat Moderation

**Provenance note:** requested directly by the user on 2026-08-25, as a targeted audit-and-fix pass on top of Phase 11 rather than new product scope. The ask was explicit: verify the dating module end-to-end, brainstorm and implement anything genuinely missing, run real API tests looking for validation gaps or crashes, and cover four named requirements — strict opposite-gender Breeding matching (with mandatory pet gender at creation), same-owner pets never matching each other, real-time chat over sockets with unmatch archiving the conversation, and chat deletion/reporting. This phase documents what the end-to-end audit actually found and what changed as a result.

### What the audit found

Reading Phase 10/11's own Status sections against the live code turned up four real gaps, none of which were previously flagged anywhere in this roadmap:

1. **`Pet.gender` was optional free text, and nothing in `dating/` ever read it.** Discovery/swipe for `BREEDING` mode only ever checked species — two same-gender pets of the same species matched each other freely, which defeats the actual purpose of a "breeding" pool. Confirmed via `grep`: `gender` appeared in exactly one place in `dating/` — nowhere. This is a correctness gap, not a hardening nice-to-have: a breeding feature that doesn't enforce sex is arguably actively harmful (surfaces genuinely unusable matches as if they were viable).
2. **Same-owner match prevention existed in `discover()` but not in `swipe()`.** `discover()` correctly excludes the caller's own pets from the candidate pool (`PetsService.findIdsForOwner`), but `POST /dating/swipe` never re-checked this server-side — a client could call it directly with `toPetId` set to one of its own other pets (never having gone through `discover()` at all) and produce a real `Match` between two pets owned by the same person. Exactly the class of bug this codebase's own convention (re-validate server-side, never trust that a client came through the "correct" flow) exists to catch — and Phase 10/11 missed it here.
3. **Chat was pure REST, no real-time layer at all.** No `@nestjs/websockets`/`socket.io` dependency existed anywhere in the app. `POST .../messages` persisted a message with no way for the other side to learn about it except polling `GET .../messages` themselves. Not what "matched chat" should mean in a dating product.
4. **No way to delete a conversation, and reporting only ever targeted a profile, never a conversation.** `DatingReport` had no way to attach chat context — a user being harassed in-match had no way to report *that*, only the other pet's profile in the abstract, and admin reviewing such a report had no way to see the actual messages.

**A fifth, more serious finding, surfaced by actually driving the module through real HTTP rather than mocks:** building the e2e coverage below (deliberately adding several back-to-back `POST /pets` calls, something no prior e2e suite had done more than once or twice) tripped a **pre-existing production bug in the global throttler config**, unrelated to `dating/` itself — see below.

### Tasks

**Mandatory, structured pet gender + strict opposite-gender Breeding**
- [x] Added `PetGender` enum (`common/enums/pet-gender.enum.ts`: `MALE | FEMALE`). `Pet.gender` changed from `@Prop({ default: '' })` (free text, always optional) to `@Prop({ type: String, enum: PetGender, required: true })`. `CreatePetDto.gender` changed from optional `@IsString()` to required `@IsEnum(PetGender)` — a pet can no longer be created without a sex on file, platform-wide, not just for pets that opt into dating. **Clean break, no migration**, per this project's own established precedent (Phase 2/7/11 all made the same call): no production pet data exists yet.
- [x] `PetsService.findIdsBySpeciesAndGender(species, gender)` — new, additive method mirroring the existing `findIdsBySpecies`, used by `discover()`'s `BREEDING` branch to filter at the query level (species AND the swiping pet's *opposite* gender) rather than post-filtering an already-paginated page.
- [x] `DatingService.discover()`: `BREEDING` mode now calls `findIdsBySpeciesAndGender(pet.species, oppositeGender(pet.gender))` instead of `findIdsBySpecies(pet.species)` alone. `PLAYDATE` is unaffected — still species- and gender-agnostic, per Phase 11's existing design.
- [x] `DatingService.swipe()`: `BREEDING` mode now also rejects `fromPet.gender === toPet.gender` (in addition to the pre-existing species check), server-side, independent of whatever `discover()` already filtered — the same "never trust the client came through the intended flow" principle already applied to the species check.

**Same-owner match prevention, closed at the actual write path**
- [x] `DatingService.swipe()` now rejects outright when `toPet`'s owner equals the caller (`ownerId`), before any mode/species/gender checks — regardless of mode. `discover()`'s existing exclusion is unchanged and still the first line of defense (a user's own pets should never even be *shown* to each other), but this closes the gap where a direct API call could bypass it.

**Real-time chat over Socket.IO**
- [x] Added `@nestjs/websockets`, `@nestjs/platform-socket.io`, `socket.io` (runtime) and `socket.io-client` (dev, for e2e). New `DatingGateway` (`src/modules/dating/dating.gateway.ts`), namespace `/dating`.
- [x] **JWT-authenticated at connection time**, not per-event: the same access token used for the REST API is passed via the Socket.IO handshake (`auth.token`, or a bearer `Authorization` header) and verified with `JwtService.verifyAsync` on `handleConnection`; a socket that fails verification is disconnected immediately — the same "no anonymous access" guarantee `JwtAuthGuard` gives every REST `dating/` route. On successful connect, the socket joins its own personal room (`user:<userId>`).
- [x] `joinMatch`/`leaveMatch` events — joining a match's room (`match:<matchId>`) is itself ownership-checked via a new public `DatingService.assertCanAccessMatch(ownerId, matchId)` wrapper around the existing private IDOR-safe check, so a socket can no more listen in on someone else's match than a REST call could read it.
- [x] `sendMessage` socket event calls the *exact same* `DatingService.sendMessage()` the REST endpoint uses — same validation (must own a side, match must be `ACTIVE`), same persisted `Message` row. **Deliberately does not broadcast directly** — instead, `DatingService.sendMessage()`/`swipe()`/`unmatch()` emit new domain events (`dating.message-sent`, `dating.match-created`, `dating.match-unmatched`, added to the existing Phase 4 `DOMAIN_EVENTS` contract file) that `DatingGateway` listens for via `@OnEvent` and then broadcasts. This means a message sent over plain REST (e.g. from a client with no socket connection at all) still reaches a socket-connected recipient live, and a socket-sent message is completely indistinguishable from a REST one once persisted — exactly the same decoupling principle Phase 4 already established for notifications, reused here rather than inventing a second pattern.
- [x] `typing` event — broadcast to the match room (excluding the sender), no persistence.
- [x] `matchCreated`/`newMessage`/`matchUnmatched` are pushed to **both** the match room (whoever has that thread open right now) **and** both owners' personal `user:<id>` rooms (so a match or a new message can update a badge/notification even when the relevant chat screen isn't currently open) — this needed each event's payload to carry both sides' resolved owner ids (`ownerAId`/`ownerBId`), added via a new `DatingService.resolveMatchOwners()` batched lookup (reuses the existing `PetsService.findOwnersForPets`).
- [x] **Deployment note, documented directly in the gateway's own file header, not left implicit**: Socket.IO's default in-memory adapter only broadcasts within a single Node process. A horizontally-scaled deployment would need a shared adapter (e.g. `@socket.io/redis-adapter`) for an event published on one instance to reach a client connected to another — the exact same class of caveat Phase 8 already documented for the in-memory throttler storage. Out of scope for a single-instance deployment, flagged here for whenever horizontal scaling is actually in play.

**Unmatch archives the chat, explicitly**
- [x] `Match` gained `unmatchedBy: Types.ObjectId | null` and `unmatchedAt?: Date`, set together with the existing `status → UNMATCHED` flip in `DatingService.unmatch()`. `unmatch()` is now also idempotent — a second call on an already-unmatched match returns `{ message: 'Already unmatched' }` rather than re-emitting events or re-touching the document.
- [x] **Behavior change, deliberate**: `DatingService.listMatches()` previously filtered to `status: ACTIVE` only — an unmatched conversation disappeared from the list entirely, which made "the history stays readable" (already true — `listMessages()` never checked status) practically unreachable, since the frontend had no way to even navigate back to it. `listMatches()` now returns both `ACTIVE` and `UNMATCHED` matches (the frontend distinguishes via `status`/`unmatchedAt` — see the blueprint update below), which is what "archived" is meant to mean here: kept, visible, read-only — not hidden.
- [x] `unmatch()` emits `dating.match-unmatched` (see the Socket.IO section above) so an open chat screen reflects the end of the match immediately — composer disabled, "this match has ended" shown — without the other side needing to poll or refresh.

**Chat deletion & reporting — brainstormed and implemented**
- [x] **Delete is a per-side, post-unmatch soft delete, not a hard delete.** `Match` gained `deletedBy: Types.ObjectId[]`. New `POST /dating/matches/:matchId/delete` (`DatingService.deleteChat`) requires the match to already be `UNMATCHED` (you can't delete a conversation out from under someone you're still matched with — unmatch first) and adds the caller to `deletedBy`, idempotently. `listMatches()` excludes any match the caller has deleted from their own list; the other side (if they haven't also deleted it) is unaffected. **Deliberately never a hard delete, even once both sides have deleted**: the underlying `Match`/`Message` documents are always kept, so a `DatingReport` referencing this match (see below) — filed before or after either side deletes — can still be reviewed by admin with full context. This was the actual design question in "brainstorm how to improve this section": a literal delete-on-request would let a harasser delete the evidence of their own harassment before it's reviewed. The chosen model (WhatsApp/Messenger's "delete for me," not a real purge) is the standard resolution to that exact tension.
- [x] **Reporting can now be filed with chat context, and admin can see the chat behind a report — both new.** `CreateDatingReportDto` gained an optional `matchId`; `DatingReport` gained a matching optional `matchId` field. When provided, `DatingService.report()` requires the reporter to own a side of that match **and** requires `targetPetId` to genuinely be the *other* side (not just any pet that happens to appear in the match — this specifically stops a reporter naming their own pet as the "target" while still attaching match context to pad out a report). New admin endpoint `GET /admin/dating/reports/:id/messages` (`DatingService.adminGetReportMessages`) returns that match's full message history — on-demand only (never inline in the report list), and audit-logged (`dating.chat.viewed`) every time it's opened, mirroring the exact pattern Phase 11 already established for admin NID review.
- [x] **Brainstormed, not implemented — flagged as backlog rather than built speculatively**: an automated content-moderation pass on message text (profanity/harassment detection) before persistence, and per-message (not per-conversation) reporting for pinpointing a single offending message rather than the whole thread. Both are real, common improvements to a chat-reporting flow, but neither was asked for explicitly and both would need a product decision (what to block vs. flag vs. allow-and-log) this phase wasn't scoped to make unilaterally.

**A larger finding along the way: a pre-existing throttler bug affecting every undecorated route in the entire app, not just `dating/`**
While building this phase's e2e coverage — which, for the first time in this codebase's history, calls `POST /pets` more than five times in quick succession from the same test run — every call past the fifth started failing with `429 Too Many Requests`, despite `PetsController.create` never having had a `@Throttle` decorator of its own and the app-wide `default` tier's limit (100 req/min) being nowhere close to exhausted. Root-caused by reading `@nestjs/throttler`'s actual `ThrottlerGuard.canActivate()` source rather than guessing: with multiple named tiers registered in `ThrottlerModule.forRoot([...])` (`default`, `public`, `write`, `swipe` — the last three added across Phases 1 and 10), the guard checks **every** route against **every** tier on **every** request, not just whichever tier a route's own `@Throttle` decorator names. A route with no decorator at all still gets checked against `public`/`write`/`swipe` using each tier's *global* default from the `forRoot()` array — so `POST /pets`, having no decorator, was silently capped at the `write` tier's 5 req/min default the entire time, completely unrelated to its own actual traffic shape. This has been true since Phase 1 (when `write` was introduced) and affects **every** undecorated route across the whole app, not just this module — it simply never got exercised by any prior e2e suite, none of which called the same undecorated route more than five times inside one minute.
- [x] **Fixed at the root, not worked around**: `public`/`write`/`swipe`'s *global* defaults in `ThrottlerModule.forRoot(...)` were raised to an effectively-unlimited `1_000_000`, with the reasoning recorded directly as a comment at that exact config block so a future session doesn't reintroduce it. This changes nothing about any route that already opts in via its own `@Throttle({ write: { limit: 5, ttl: 60_000 } })` (auth register/login/etc., found-report submission, identity-verification submission) or `@Throttle({ public: {...} })` (the public tag-resolution/lost-pets routes) or `@Throttle({ swipe: {...} })` (dating swipe) — a route-level `@Throttle` override always wins over the array default regardless of its value, verified directly by `ThrottlerGuard`'s own source (`routeOrClassLimit || namedThrottler.limit`). It only stops those tiers' defaults from silently applying to routes that never named them. `default` (100/min, meant to apply to literally everything) is unchanged.
- [x] Confirmed the fix doesn't weaken anything real: `test/lost-and-found-flow.e2e-spec.ts`'s existing dedicated rate-limit assertion (bursts the `public`-tier-decorated tag-scan route past 20 req/min and expects a real `429`) still passes unmodified — that route's own `@Throttle({ public: {...} })` override is untouched by this change.

### Swagger Requirement
Applied: `PATCH`/`POST /pets` DTOs document `gender` as required (`@ApiProperty({ enum: PetGender })`, replacing the old optional free-text field); `POST /dating/matches/:matchId/delete` and `GET /admin/dating/reports/:id/messages` both carry full `@ApiOperation`/`@ApiResponse` coverage; `CreateDatingReportDto.matchId` is documented as optional with a description of when/why to set it; the `DatingController`/`AdminController` operation descriptions for `report`/`unmatch` were updated to reflect chat-context reporting and archival respectively. The Socket.IO gateway (not an HTTP surface) is documented instead directly in this roadmap section and in `PAWTATO_FRONTEND_BLUEPRINT.md`'s new chat-integration section, since Swagger has no representation for WebSocket events.

### Definition of Done
- [x] A `BREEDING` candidate pool is same-species **and** strictly opposite-gender in both directions — proven by a unit test (`discover` calls `findIdsBySpeciesAndGender` with the opposite gender) and a real-HTTP e2e test (a same-gender same-species cat never appears in the pool, and a direct `swipe` attempt against it is rejected server-side even bypassing `discover`).
- [x] Two pets owned by the same person can never produce a `Match`, proven at the `swipe()` write path directly (not just via `discover()`'s exclusion) — both a unit test and an e2e test swipe directly between two same-owner, otherwise fully-compatible (opposite-gender, same-species, both modes enabled) pets and confirm rejection.

## Phase 15 — Shared Pet Access (Caretakers)

**Provenance note:** the first item pulled from the Phase 9 Post-MVP Backlog ("Multiple authorized caretakers / shared pet access") into a real numbered phase, per the user's explicit request to work through the backlog. The other three remaining backlog items (push/SMS channels, expanded medical records, nearby lost-pet discovery, QR tag commerce) are picked up in subsequent phases — see the Phase 9 section itself for what's left.

**Goal:** Let a pet's owner grant another registered user ("caretaker" — a vet, family member, or pet-sitter) shared access to that pet, without rebuilding every module's authorization model or introducing an invite/notification subsystem. ### Scope decision, made explicit up front
A caretaker gets: view access to the pet, its medical/vaccination/scan/found-report history, and the ability to report it lost/found — the actions a real pet-sitter/vet/family member scenario actually needs. A caretaker does **not** get: profile edits, photo management, pet deletion, tag/QR management, dating-module access, or the ability to manage other caretakers. This line was drawn deliberately narrow (rather than a full owner-parity or configurable-role model) to avoid a much larger refactor touching every module's authorization boundary for capabilities no real request asked for; extending it later (e.g. a `VIEWER`/`EDITOR` role split) is a natural, additive v2 if ever needed.

- [x] Direct-add, not an invite/accept flow — the owner must already know the caretaker's registered account email; access is immediate. Deliberate simplification: building a second invitation/notification subsystem for this wasn't asked for and isn't needed for the core scenario.

### A significant, previously-undiscovered bug found and fixed along the way

Building this phase's e2e coverage (a real upload → real cascade-delete → confirm-the-file-is-actually-gone check) surfaced a genuine, pre-existing production bug, unrelated to anything this phase added: **`MedicalService.create()` and `VaccinationsService.create()` had always stored their `pet` field as a raw BSON string instead of an `ObjectId`**, despite the schema declaring `type: Types.ObjectId`. Verified directly against the raw collection (bypassing Mongoose's own schema layer) — `{"pet":"68f...9d"}`, not a real `ObjectId`. Every plain-string-filtered query (e.g. `findAll()`'s `{ pet: petId }`) still matched by pure coincidence (string equals string), which is exactly why this had never surfaced as a visible symptom — but `deleteAllForPets()`'s cascade-delete query (`{ pet: { $in: [ObjectId, ...] } }`, written correctly per this codebase's own dominant convention) never matched, meaning **every medical record and vaccination record has silently survived admin-initiated pet/user deletion since these two services were written** — orphaned indefinitely, including for deleted user accounts, a real data-retention/privacy concern, not just a tidiness one. The existing `admin-user-deletion-cascade.e2e-spec.ts` test that specifically claims to verify this had the identical blind spot (it also queries with an `ObjectId`), so it always reported "0 remaining" whether or not the cascade had actually worked — a false-positive-passing check that never caught its own gap.

Root cause, confirmed empirically (not just theorized) against this project's exact dependency versions (Mongoose 9.9.3, freshly installed): a plain-string value in a Mongoose query filter is **not** reliably auto-cast to `ObjectId` for comparison against a real `ObjectId`-typed field in this version — contrary to older, widely-known Mongoose behavior. This is exactly why this codebase's own dominant convention everywhere else (`pets.service.ts`, `dating.service.ts`, the admin cascade queries, etc.) always explicitly wraps ref values in `new Types.ObjectId(...)` rather than relying on auto-cast — `medical`/`vaccinations` were simply the two places that had quietly drifted from that convention since early in the project.

Given the severity, a follow-up audit (a dedicated read-only pass across every `src/modules/*/*.service.ts` file, cross-referencing each schema's `Types.ObjectId`/`ref` fields against every query/write site) found the same anti-pattern in two more places, both fixed in this same pass:
- [x] `ScansService.findForOwnedPet()` and `FoundReportsService.findForOwnedPet()` — identical bug, identical fix (explicit `new Types.ObjectId(petId)`). Neither had ever been exercised by an e2e test asserting on the actual returned content — `lost-and-found-flow.e2e-spec.ts` now does, for both.
- [x] `ActivityService.log()`/`findAll()` — `Activity.actor` is a real `Types.ObjectId, ref: 'User'` schema field but was always stored/filtered as a raw string. This didn't silently return empty results the way the others did (the un-cast filter still self-consistently matched the un-cast stored value), but it did silently break `.populate('actor', 'fullName email')` — the admin audit log's actor name/email has likely never resolved correctly, every entry showing an unpopulated id instead. `target` was deliberately left alone — it's a generic string label (petId/tagId/reportId/...) by design, not a single-collection ref, so there's nothing to cast there. `admin-audit-flow.e2e-spec.ts` now asserts the populated shape and the `?actor=` filter.
- [x] Audited but confirmed clean: every other `.create()`/query call site across `caretakers`, `pets`, `tags`, `dating` (all its services), `identity-verification`, `notifications`, `users`, `public`, `qr`, `health`, `admin`, `auth` — each either already explicitly casts, or only ever handles values taken directly off an already-fetched Mongoose document (which are real `ObjectId` instances at runtime, never a bare string).

### Swagger Requirement
Applied — the four new document endpoints (`MedicalController`/`VaccinationsController`) have full `@ApiOperation`/`@ApiConsumes`/`@ApiBody`/`@ApiResponse` coverage, matching `PetsController.uploadPhoto`'s existing multipart-upload documentation pattern.

### Definition of Done
- [x] A medical or vaccination record's owner or an authorized caretaker can upload (image or PDF, ≤10MB) and remove document attachments.
- [x] A disallowed file type or oversized file is rejected with `400` before it touches disk.
- [x] Removing a document deletes its stored file; an already-removed document is a clean `404`.
- [x] Cascade delete (admin-initiated *and*, newly, owner self-service) removes every attached file, not just the database reference — proven directly against the filesystem, not mocked.
- [x] The `pet`-field ObjectId-casting bug (and its two related instances) is fixed and covered by real, DB-backed e2e assertions that would have caught it, not just unit tests against mocks.
